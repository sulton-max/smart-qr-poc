## Iteration 1 — Dynamic-by-default content model (design pass)

> **SUPERSEDED 2026-07-22 → `version-track/v0.9/v0.9.md`.** This iteration's thesis *is* v0.9's — the per-code static/dynamic axis + rules-on-any-content. v0.9 took it further (CM15: a rule carries content) and is **building it** (`8477648`..`80a3529` + staged changeset): `isDynamicType`/`IsStatic` already deleted, an explicit `Mode` field added. Nothing to design here — this was the seed, v0.9 is the tree. Left for provenance.

**Insight (2026-07-11):** the static/dynamic split is a **per-code choice, not a per-content-type trait**. *Any* content type can carry routing rules (dynamic) or bake its payload (static) — e.g. a `Phone` that routes to person A on even days / person B on odd, or a `WiFi`/`MobileApp` with rules. Some codes stay static by choice. This overturns `isDynamicType(id)` (`domain/codes/content/operations.ts` — currently hardcodes `url`/`mobileApp` as dynamic) and reshapes the picker's static/dynamic filter.

Full design analysis to align **back + front** *before* touching the forms:

- [ ] Replace `isDynamicType` with a per-code `ResolutionMode`
- [ ] Make rules attachable to every `CodeContent`
- [ ] Gate resolution and rule evaluation on the code's mode
- [ ] Resolve every content type via the forwarder short link
- [ ] Replace the picker's static/dynamic filter with a toggle
- [ ] Draw the static vs dynamic design mocks
- [ ] Pick a default mode per content type
- [ ] Reconcile with the marketing content-type capture
- [ ] Hand the settled contract to Iteration 2
