## Architecture

### The mechanic

- **static** → the symbol bakes the payload itself
- **dynamic** → the symbol bakes `{RedirectBaseUrl}/{slug}` — the short link
- one branch today: `code.Content.Encode() ?? shortUrl` (`CodeImageService.cs:18`), mirrored in preview (`CodesController.cs:38`)
- the two symbols' **bytes differ** → static and dynamic are physically different codes; no in-place flip exists for something already printed

### The core problem — bakeability is not a content property

R3 moved the `url` destination **out of content and into a `Default` rule** (`createCodeForm.ts:194-197` appends it at submit). So content alone can no longer answer *"can this bake?"*:

- **one rule** → the destination is fixed → **can** bake (unless the user chose dynamic)
- **two or more rules** → the destination is decided at scan time → **must** be dynamic

`CodeContent.IsStatic => Encode() is not null` (`CodeContent.cs:26`) is therefore **structurally wrong, not merely misnamed** — it asks a whole-code question from inside the content object, which cannot see the rules.

The `Encode() : string?` signature is the same error surfacing as a smell: `UrlContent.Encode()` returns `null` (`UrlContent.cs:17`) **not** because a URL is unbakeable — it is the most bakeable content there is — but because a url code's payload lives in its rules. The null encodes a model leak, and every service that branches on it inherits the leak.

### The unification — a rule carries content

> **Owner's insight, 2026-07-17.** Content isn't a sibling of rules. **A rule = condition + content.** Static content is content in a `Default` rule.

Stress-tested against all 10 types — **it holds**:

| Code | Rules |
|---|---|
| static `url` | `[Default → UrlContent]` |
| dynamic `url` | `[iOS → UrlContent, Android → UrlContent, Default → UrlContent]` |
| `mobileApp` | `[iOS → UrlContent(store), Android → UrlContent(store), Default? → UrlContent]` |
| static `wifi` | `[Default → WifiContent]` |
| dynamic `wifi` | `[Default → WifiContent]` — editable, served by the page |
| routed `wifi` | `[RuleA → WifiContent, RuleB → WifiContent]` |

`RuleDto.Destination` (a `string` today) generalizes to **`Rule.Content`**. `CodeEntity.Content` dissolves into `rules[].content`.

**What it collapses — four open problems, one model change:**

- **the Default circle** — the strip/append dance (`createCodeForm.ts:162,194-197`) exists *only* because `UrlContent.url` and the `Default` rule carry the same URL. Content in the rule = nothing to duplicate. The defect **dissolves**; it doesn't need fixing
- **M1's open question** — *"`MobileAppLinkContent` shrinks to a marker vs keeps its fields"* is answered: its links **are** rule contents. `mobileApp` stops being a content type and becomes a **preset** over `url` + device rules
- **`CodeContent.IsStatic`** — dies. Rule count decides, and rule count is visible where rules live
- **the 0-rules hole** — `≥1 rule` becomes the invariant, replacing today's content-required + rules-optional + Default-appended-at-submit workaround
- **V5** (`url` returns 200 on an empty URL — `validation.md`) — a rule's destination is already validated (`RuleDtoValidator.cs:15-18`); url content inside a rule inherits that

**The family split demotes.** It isn't a *model* split — one model covers everything. It's a **resolve-path** split, and that stays type-level:

| Resolve path | Types | Dynamic reaches the device via |
|---|---|---|
| **Redirect** | `url` · `geo` *(· `mobileApp` as a preset)* | 302 to `content.Encode()` |
| **Page** | `wifi` · `vCard` · `calendar` · `text` · `phone` · `sms` · `email` | page serves `content.Encode()` |

- `Encode()` becomes universal — *"the payload of this content"*. Static bakes it; a Redirect-path dynamic 302s to it; a Page-path dynamic serves it. **One method, three call sites, no nulls**
- two clean axes: **resolve path** = a type property · **mode** = a code property constrained by rule count

**Riders — where it strains:**

- **content *type* is code-level; content *value* is rule-level.** `[iOS → vCard, Android → WiFi]` is incoherent — a code is "a WiFi code". Homogeneity is an invariant: either `CodeEntity.ContentType` stays, or it derives from `rules[0]` and gets validated
- **static stores a rule the router never evaluates.** Live data (it's what gets baked), just never matched — so CM13's *dead-by-construction* reasoning does **not** extend to it. Don't conflate the two
- **scope** — dropping `CodeEntity.Content` restructures entity, DTO, form, validators, redirect and migrations. This is the content model **v2**, not "add a mode field"

### Decisions

| # | Decision | Rationale |
|---|---|---|
| CM1 | Bakeability = **f(content, rules)** — never content alone | R3 moved the url destination into a `Default` rule. `CodeContent.IsStatic` (`CodeContent.cs:26`) cannot see rules, so it cannot answer |
| CM2 | **`rules.Count > 1 ⟹ Dynamic`** — an implication, **not** an equivalence | Two destinations can't be baked, so 2+ rules *forces* dynamic and the UI locks the control. One rule does **not** imply static: a single-URL code the user wants to edit later is dynamic **by choice, from the start** — the whole point of the axis. Mode is a stored choice that rule count only *constrains* |
| CM3 | Mode chosen at **create**, **locked** after | The symbol leaves the app the moment it exists — printed, screenshotted, forwarded. A download event isn't the signal; a screenshot is just as final. Locking at create needs **no new column** |
| CM4 | **No in-place flip**, either direction | Static→dynamic leaves every printed copy carrying the baked payload — the flip silently does nothing for them. Dynamic→static is worse: printed copies keep hitting the server, so you either keep resolving (flip is cosmetic) or break them (violates never-expire) |
| CM5 | Mode change = **a new code**, both directions | "Make a dynamic copy" / "make a static copy" — copies content, mints a new symbol. One click, not a re-do |
| CM6 | **Pre-create notice** on a static choice | State that the payload is baked and any later content change yields a different symbol; offer dynamic inline. The user is holding the print decision at that exact moment |
| CM7 | Mode = a **chip on the code card**; never in the type picker | Two orthogonal axes — *what it carries* vs *how it resolves*. Merging gives 20 dropdown entries |
| CM8 | Dynamic offered for **every** type | "Only-static" is a current-infra limit, not a property of the content. WiFi/vCard/calendar most need edit-after-print |
| CM9 | Dynamic non-URL → a **minimal, styleless resolve page** | A dynamic WiFi code can't 302 to `WIFI:T:WPA;S:…;;`. Ship a bare page that hands the payload to the device; the designed/editable version is the backlog's *Dynamic content pages* venture |
| CM10 | Editing a static code's content → **a version** of the same code | Deferred (~v0.12+). Without it, a rotating WiFi password accumulates unrelated codes. Branching to a separate code stays available |
| CM11 | **Paywall deferred** | Decide once the axis works end-to-end; audit columns + payment design come with it. A paywalled arm needs an upsell state, not a disabled one — a later UI delta, not a blocker |
| CM12 | **Keep the slug** — don't reuse the entity `Guid` | The slug's job is to be **short**, not readable — that's what a GUID can't do. `https://host/aB3xY9k` ≈ 23 chars → ~25×25 symbol; a raw GUID path ≈ 47 chars → ~33×33; base62-encoded still ~29×29. More modules at fixed print size = shorter scan distance, less damage tolerance — against the "dynamic = cleaner symbol" advantage. Vanity slugs are a likely paid feature (*Custom domain* is already the $5 wedge) → a GUID path forecloses them or forces the slug back. PK-as-public-id is a one-way door: a code can be re-slugged, a row can't be re-keyed. Cost of both: 7 bytes + one unique index. The GUID isn't wasted — it stays private |
| CM13 | **Slug + `shortUrl` minted for dynamic only**; `Slug` nullable | Under CM4+CM5 a static code's slug is **unreachable by construction** — mode never flips, and a copy mints its own. Dead-by-construction data shouldn't exist. Nullable + unique works in Postgres (NULLs aren't equal); the redirect's `c.Slug == slug` probe never matches NULL. Kills the `shortUrl`-shown-for-static defect (`p0.1` § *Defects + drift*) structurally rather than by remembering to gate every consumer |
| CM14 | `tel:` / `sms:` / `mailto:` → **page first**; 302-the-content is a later spike | Browsers block or drop http→custom-scheme redirects (a known abuse vector), so `Location: tel:+123` is unreliable across scanners. The page carries a tappable link |
| CM15 | **A rule carries content** — `Rule.Content` replaces `Rule.Destination`; `CodeEntity.Content` dissolves into `rules[].content` | Static content = content in a `Default` rule. Collapses the Default circle, M1's marker question, `IsStatic`, the 0-rules hole and V5 into one model change. Content *type* stays code-level (homogeneity invariant); content *value* is per-rule |
| CM16 | **Resolve path is a type property; mode is a code property** | `Redirect` (`url` · `geo`) vs `Page` (`wifi` · `vCard` · `calendar` · `text` · `phone` · `sms` · `email`) is intrinsic to what the payload *is*. Mode is the user's choice, bounded by CM2. Keeping the axes apart is what stopped `IsStatic` from being repairable in place |
| CM17 | **A static code never reaches `Redirect.Api`** | Its symbol carries the payload (`WIFI:…` / `https://target`), so the scanner goes straight to the target or the OS handler. Our server is never in the path. Corollaries: the single rule is never *evaluated* (only baked) · the slug is never resolved (CM13) · scan analytics is structurally impossible, not merely absent |

### Open forks

**F1 — `Encode() : string?` — leaning, NOT locked**

> **Deliberately open (owner, 2026-07-17).** CM15 changes content shapes; picking encoding's home before the shapes exist is premature. F5 may move it again. Recorded as reasoning to revisit, not a decision.

*Considered:* extract encoding to a service that takes content and encodes it, so the method is unreachable for dynamic content.

*Leaning:* **keep `Encode()` polymorphic on the content; drop the `?`.**

- an extracted encoder needs a per-type `switch` or registry — **exactly what M1 is deleting** (`IContentTypeSpec` + `ContentTypes`). Resurrecting a registry one iteration after removing one is a regression
- polymorphism already gives per-type dispatch for free, with no registry and no switch
- the null had **two causes, both gone**: `url` (payload lives in rules → *the rule's* content encodes it) and `mobileApp` (dissolves into a preset under M1). Nothing else ever returned null
- **reachability is a call-site property, not a signature property.** One payload resolver owns the three call sites (bake · 302 · page); hiding the method doesn't add enforcement, it adds indirection
- `CodeContent` stays data + its own encoding — which is cohesion, not behaviour leakage. `IsStatic` was the leak, and it dies

**F2 — the `url` fork — resolved by the unification**

M1's *"marker vs fields"* question is answered: `UrlContent.url` **doesn't survive as a code-level field**; the destination is the rule's content. Both lanes now have the same answer — **v0.9 owns it, `p0.1` consumes it**. See § *Lane split*.

**F4 — the optional fallback: `Default` is a role, not a condition**

*Requirement (owner, 2026-07-17):* the fallback is **optional** — no match may legitimately 404. When wanted, the user either authors a dedicated fallback **or nominates an existing rule** (mobileApp: "use the iOS link for everyone else"). Applies to every dynamic type, not just `mobileApp`.

*Shape (owner, 2026-07-17) — a polymorphic rule hierarchy. No nullables, no dead members:*

```
CodeRule (abstract)                                    // JSON-polymorphic, discriminated
├── ConditionalRule    { Order, Condition, ConditionValue?, Content }
├── DefaultRule        { Content }                      // no Order, no Condition — never matched, always last
└── DefaultPointerRule { TargetOrder }                  // no Order, no Condition, no Content
```

- **at most one** `DefaultRule | DefaultPointerRule` per code — the **one-default invariant**
- **absent** → no fallback → **404**. The rule list carries the optionality; the code needs no field for it
- *dedicated fallback* → `DefaultRule`
- *nominate the iOS rule* → `DefaultPointerRule { TargetOrder = <iOS rule's order> }`
- *static* → exactly one rule; never evaluated (CM17), only baked

*Superseded — the earlier `Code.FallbackRuleOrder?` + `Condition?` shape:*

- the code-level pointer was **redundant** — presence of a `Default*` rule in the list already encodes "has a fallback"
- `Condition?` nullable was a **member that only exists to be absent** — inheritance expresses that with no nullable at all
- `Order` on a default was likewise dead: a fallback is last **by definition**, not by position

*Pointer target — `TargetOrder`, not an id (owner, 2026-07-17):*

- `Order` is already the rule's identity within a code — no second id needed
- reorder rewrites `TargetOrder` in the same operation that rewrites `Order`
- no `Guid` to mint client-side at create — pointer works before the server assigns anything
- *(rejected: a stable `Id`. It only pays off if a pointer must survive an unsynchronized reorder — reorder is one atomic write here)*

*Cycles — guarded by the one-default invariant, not by structure:*

- a `DefaultPointerRule` takes the single default slot
- every other rule is a `ConditionalRule` → holds content
- → a target always holds content, never another pointer
- must be **validated**, not assumed

*Kills defect D2 structurally* — `Default` stops being a selectable `RuleConditionType`, so no duplicate can be authored. The defect existed because a *role* masqueraded as a *condition*.

*Exclusive-members bar — resolved 2026-07-17: the hierarchy is exempt.*

- convention now carries a role carve-out (`backend/code-style/models.md` § *the exclusive-members bar*)
- bar targets a **second representation of one instance**; union siblings are different things in one list
- test added: subset + *"could the existing type carry this instance?"* → **no** → keep
- `DefaultRule` cited there as the exempt example

*Open:*

- **`MatchedRuleId` on a pointer resolve** — the pointer or its target? Analytics reads `RouteDecision.MatchedRuleId`

**F5 — render/redirect resolution** *(partially resolved 2026-07-17)*

*Resolved — `Rule.Content` is **one** type (`CodeContent`):*

- 3 consumers: **bake** (string) · **302** (URL) · **page** (structured data)
- all 10 types encode to a string → bake satisfied by one type
- 302 needs that string to be a URL; `WIFI:T:WPA;…` is not a valid `Location`
- that's a **constraint on which types take the Redirect path**, not a second shape
- CM16 already makes resolve path a type property → the constraint has a home
- paths differ in what they **do** with `Encode()`, not in what they store

*Storage ≠ routing (owner, 2026-07-17):* one *base* type, still **one model per content type**. The per-content models were right; they get refined as they move inside rules, not merged.

*`UrlContent { url }` as a 1-field wrapper — not a problem.* Same union-sibling exemption: it co-exists with `WifiContent` et al. in one discriminated union, and the discriminator is load-bearing.

*Deferred — the full shape.* `ConditionalRule.Condition` + `ConditionValue?` is undecided and sits in the same hierarchy. Settle the condition model before closing rule member lists.

**F3 — resolve-page host**

SPA (`/c/{slug}` route, 302 from `Redirect.Api`, `RouteOutcome` stays 3-valued) vs a new HTML surface in `Redirect.Api` (`Program.cs` is 9 lines, no view engine). The backlog's *Dynamic content pages* already says smart-qr *"creates the page + forwards to it"* → 302-to-SPA looks decided.

### Content models — swept 2026-07-18

**Type set: 10 built.** Backend `CodeContentType` declared **26**; the 16 unbuilt drop (logged in `feature-research.md` § *Content-type templates*). FE enum already carried exactly 10 — the divergence dies with the trim.

**Per-type verdicts:**

| Type | Members | Verdict |
|---|---|---|
| `url` | `url` | confirmed as-is |
| `text` | `text` | confirmed as-is |
| `phone` | `phone` | **string** — see below |
| `sms` | `phone` · `message?` | **string** |
| `email` | `to` · `subject?` · `body?` | confirmed as-is |
| `geo` | `latitude` · `longitude` | `string` → **number** |
| `calendar` | `title` · `start` · `end?` · … | `string` → **`Temporal.PlainDateTime`** |
| `wifi` | `ssid` · `password?` · `encryption?` · `hidden` | `encryption` → **enum** |
| `vCard` | `firstName` + 9 optional | `phone` stays **string** |
| `mobileApp` | `appStore?` · `playStore?` · `other?` · `fallback?` | **reshape** → `{ Store, Url }`, `Store` = new enum |

**Phone numbers stay `string`** — not a number type:

- leading `+` and country code are semantic, not arithmetic
- leading zeros are significant in national formats; numeric types drop them
- extensions (`x123`), spaces, dashes are part of user input
- no arithmetic is ever performed on a phone number
- E.164 is a **string** format; validate by pattern, not by type
- same rule for `vCard.phone` and `sms.phone`

**`mobileApp` reshape — DECIDED 2026-07-18:** `MobileAppLinkContent { Type, Url, Store }`.

- **the model survives** — it does *not* dissolve into bare `url`; `Store` is its exclusive member
- `Store` = new `StoreType` enum — `Ios` · `Android` · `Other` (extend as stores are added)
- **`other` and `fallback` members drop** — today's 4 loose optionals permit a code with **zero** links
- a `DefaultRule` may carry **any** `StoreType` value
- a `DefaultPointerRule` may target an iOS-conditional rule, so an iOS link legitimately serves as the catch-all
- `Store` is not a device — the device lives in `ConditionalRule.Condition`, the store in the content

**Enum trim applied 2026-07-18** — `CodeContentType` 26 → 10; build green.

- `CodeContentPolymorphism` reflects over **types**, not enum members → unaffected
- **`IsSupported()` is now tautological** — the enum equals the supported set
- `CodeContentTypeExtensions` + the gate at `ContentValidation.cs:19` are dead
- **conflicts with `p0.1` M1**, which plans to *keep* that gate — flagged to that lane

**Optionality — 4 categories.** No content type has server-side field validation except `mobileApp` (`validation.md` V4), so every optional below is currently unenforced.

| Category | Fields | Action |
|---|---|---|
| Genuinely optional | `email.subject/body` · `sms.message` · `calendar.end` · `vCard.org/title/note/address` | keep optional |
| **Conditionally required** | `wifi.password` — required unless `encryption = nopass` | cross-field rule |
| **Unvalidated ranges** | `geo.latitude` (−90..90) · `geo.longitude` (−180..180) · `calendar.end > start` · `url` scheme | add constraints |
| **Wrongly optional** | `mobileApp.*` — all 4 optional permits an empty code | fixed by the reshape |

3 files in `integration/codes/models/`. Findings:

**Open:** does preview take a full `CodeCreateUpdateApiRequest`, or stay a distinct type? It has no `name`, so today it is not a subset — the exclusive-members bar applies once `value` drops.

**Optionality → validation rules.** The 4 categories above become the content-validation spec once models close. Destination: `engineering/architecture/` (routing-engine or a content doc), per the 2-layer split. Don't re-derive them at validation time.

Open: whether `vCard` requires ≥1 contact method (`phone` / `email` / `url`) — a validation constraint, not new fields. Product call. *(Social handles + multi-person vCard are separate features — logged in `feature-research.md`.)*

### Deferred to a later version — DRY the E2E contract mirror

`SmartQr.Tests.E2E/Support/ApiContracts.cs` (111 lines) hand-mirrors `CodeDto` + the rule union. It drifted twice already: the `vCard`/`vcard` discriminator bug (`1953f71`) and the stale preview bodies the v0.9 sweep found (compiled clean, would have 400'd at runtime).

Three options, in preference order:

- **(a) reference the real assemblies.** `SmartQr.Tests.E2E` already references the host (it boots it via `WebApplicationFactory`), so `CodeDto` and `CodeRule` are *already reachable* — the mirror is redundant, not required. Cheapest by far; check first before building anything.
- **(b) a shared `SmartQr.Contracts` library** holding DTOs + requests, referenced by Api and tests. Cleaner layering, but a real restructure — and the SDK-extraction baskets (`SmartQr.Common.*`) already occupy that role.
- **(c) keep the mirror.** Defensible only as a *contract test*: an independent shape that fails when the wire changes. That is a deliberate choice, and today's mirror isn't one — it drifts silently instead of failing loudly.

**Caveat against (a):** deserializing into the server's own types can hide a serialization bug, since both sides share the converter config. Mitigate by keeping a handful of raw-JSON assertions on the discriminator and casing.

Verdict: **try (a) first**, keep 2–3 raw-JSON shape assertions as the anti-drift guard. Not v0.9 — the suite is green and this is a refactor, not a fix.

### Lane split

> CM15 moves the boundary. The content model is now v0.9's; `p0.1` keeps the mechanical polish. Agreed 2026-07-17.

**v0.9 owns** — everything the content-in-rule model decides:

- the `url` fork / M1's *marker vs fields* — **answered** by CM15 (`p0.1` Iter 12 M1)
- **M1b + the Default circle** — the circle **dissolves** under CM15; don't fix it, don't design around it (`p0.1` Iter 12)
- **content validation restructure** — `validation.md` V1–V7. Its own note says *"owner is handling content-type shape in a separate chat"* — that chat is this one, and CM15 decides the shape validation must fit. **The 2-layer split (presentation + persistence/infrastructure) analyzes here**
- content-type shape generally — `ContentTypeDescriptor` · the catalog · per-type semantics

**`p0.1` keeps** — no dependency on the content model:

- R1 (done) · R2 close-out · R5 deferred · docs pass · defect-list numbering · fallback-copy purge
- Iteration 14 (select-field + calendar) · Iteration 15 (test naming)
- **defects D1 + D2** — both stem from *the builder offers routing the submit path discards*. CM15 removes the discard path entirely, so **coordinate before fixing**: a fix now is rework

**M1's status changes** — its stated goal (delete `IContentTypeSpec` · `ContentTypes` · `MobileAppLinkContentSpec` · `ContentProjection`) still holds and is still `p0.1`'s. Only its *open sub-decision* moves here.

### Model sweep — order (owner, 2026-07-18)

> CM15 is a content-model **v2**, so shapes get re-derived rather than patched. Conventions: `frontend/code-style/models.md` (FE taxonomy) · `backend/code-style/models.md` (polymorphic models, exclusive-members bar).

**Sweep BE + FE together per layer**, innermost first:

`content → condition → rule → code + entity → requests + serialization → forms + components`

- **symmetry per layer beats one-type-end-to-end** — CM15 changes *containment*, not just field types
- a single content type can't be traced through a container that doesn't exist yet
- BE↔FE drift is caught at each layer, not at the end (`vCard`/`vcard`, `1953f71`)
- **serialization sits with requests** — the last structural layer before the UI consumes it
- **forms + components last** — they're the only layer with no downstream dependents
- tree stays RED between layers; that's the cost of a v2, not a defect

### Polymorphic serialization — `SubtypeRegistry` (2026-07-19)

Two bespoke resolvers (`CodeContentPolymorphism` · `CodeRulePolymorphism`, ~50 lines each) collapsed into one generic type. Lives in `SmartQr.Common.Domain/Serialization/` — an SDK-extraction basket, pre-positioned for the backend-beta lift the convention already anticipates (*"extract the reusable resolver once a 2nd union appears"*).

**Two layers, deliberately split** — fusing them would force a rewrite for a non-JSON format:

- `SubtypeRegistry<TBase, TKind>` — the `(kind → type)` set + validation. Serializer-agnostic
- `.ToJsonModifier()` — the System.Text.Json binding, an extension. XML later = `ToXmlBinding()`

**Declared on the base**, since a closed union's base should know its variants:

```csharp
public static readonly SubtypeRegistry<CodeRule, CodeRuleType> Subtypes = new(
    (CodeRuleType.Conditional, typeof(ConditionalRule)),
    (CodeRuleType.Default, typeof(DefaultRule)),
    (CodeRuleType.DefaultPointer, typeof(DefaultPointerRule)));
```

**Fails at boot, not on first request** — wiring reads the static field, which forces type init, which runs the ctor's validation: every `TKind` member mapped exactly once · every type derives from `TBase` · no duplicates or abstracts.

**What it removed:**

- `RuntimeHelpers.GetUninitializedObject` — the ghost-instance trick, both sites
- the `Type` property + `[JsonIgnore]` on **13** variants (10 content + 3 rule)
- `KindOf(instance)` replaces it for generic dispatch; pattern matching for branching

**Naming** — `Registry` is the sanctioned suffix (`component-names.md:33`, *"lookup of pre-registered items"*). Rejected `JsonUnion`: the declaration isn't JSON's, and `Union` is the TS idiom for a language feature C# lacks.

**Wired at both serialization layers** — MVC `JsonOptions` (API) and `CodeContentJson.Options` (jsonb). Rules need the jsonb wiring only under Iteration 5's fork (b).

*Deferred:* a generic `content.Kind()` extension usable across any union — ergonomic sugar over `KindOf`, no behaviour change.
